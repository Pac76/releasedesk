# RD-002 — Supabase foundation, schema, and RLS

## Task brief

Prepare ReleaseDesk for a future Supabase project without remote mutations or committed credentials. The increment required typed SSR client factories, a CLI-generated reproducible migration, least-privilege grants, owner-scoped RLS, database-enforced project/work-item ownership consistency, policy tests, aligned database types, and setup documentation.

## Develop handoff

Develop pinned the current Supabase JS, SSR, and CLI packages; initialized the local Supabase layout through the CLI; and generated the migration and pgTAP test files with CLI commands. The migration defines `projects` and `work_items`, validation constraints, deliberate cascades, query indexes, update triggers, a composite owner/project foreign key, minimum grants, and eight operation-specific RLS policies.

The TypeScript layer adds typed browser/server clients and explicit, non-secret configuration errors. Public pages do not instantiate a client, so the application builds without configured values. Database types are manually aligned with the migration and clearly documented as pending regeneration from the future project.

Develop's final application checks passed with 11 Vitest tests.

## Testing verdict

**APPROVED — review round 1.**

Testing independently reviewed the migration, clients, types, tests, dependencies, documentation, Git ignore behavior, and credential-shaped patterns. It confirmed:

- `anon` has no table privileges;
- `authenticated` receives only select/insert/update/delete;
- both exposed tables have RLS enabled;
- all four operations have distinct owner policies;
- both update policies contain `USING` and `WITH CHECK`;
- work-item policies and the composite foreign key both enforce owner/project consistency;
- public production builds remain independent of configured Supabase values.

No BLOCKER or MAJOR finding remained.

## Local Supabase limitation

Supabase CLI `3.4.0` downloaded its local images but failed on this Windows host before applying the migration. Both the npm wrapper and direct native executable reported that a generated argument contains a `cmd.exe` special character. The attempted stack stopped cleanly and no project containers remained.

Therefore the pgTAP suites were statically reviewed but not executed. No remote project, schema, or credential was used. This is recorded as an unexecuted check, not a pass. The suites can run later through WSL/Linux or after applying the migration to the user-created Supabase project.

## Orchestrator verification

The Orchestrator inspected the SQL and TypeScript clients directly, confirmed `.env.local` is ignored without reading or printing its contents, and reran the repository checks.

The local Supabase foundation is approved. Applying the migration, regenerating remote types, running advisors/pgTAP against a working database, and connecting production environment variables remain explicit future integration steps.
