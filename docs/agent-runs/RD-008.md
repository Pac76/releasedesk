# RD-008 — Bilingual English and Spanish product interface

## Orchestrator task brief

### User-facing outcome

An English-speaking prospective client sees natural US English by default, while any visitor can switch the complete ReleaseDesk interface to Spanish and keep that choice across journeys. Product behavior, design, data model, authentication, and core architecture remain unchanged.

### Scope

- Preserve the complete original Spanish interface and add natural, concise US English equivalents.
- Add a visible EN/ES language control that defaults new visitors to English and persists the selected locale across public, authentication, and protected routes without a hydration flash.
- Cover the landing page, navigation, authentication, dashboard, projects, work items, repository intelligence, loading/empty/error/not-found states, form help, confirmation text, validation feedback, server-action feedback, readiness labels/evidence, status/priority labels, date presentation, and relevant metadata in both languages.
- Update tests whose assertions encode visible copy.
- Adjust only copy-driven layout details when necessary to prevent responsive overflow.
- Update the product-language decision in `AGENTS.md`, `docs/APP_SPEC.md`, and the workflow plan.

### Out of scope

- A third-party internationalization dependency, locale-specific URL routing, machine translation, or support beyond English and Spanish.
- Visual redesign, new functionality, new dependencies, or component restructuring unrelated to copy fit.
- Business logic, database schema/data, Supabase policies, authentication behavior, GitHub integration behavior, or deployment architecture.
- Translating technical documentation beyond the language-policy and truthful agent-run record.

### Observable acceptance criteria

1. Every user-visible product string in `src/` has natural US English and Spanish output, including success, error, validation, empty, loading, confirmation, and readiness evidence states.
2. New visitors see English, the EN/ES control is keyboard-accessible, and the selected locale persists across navigation, authentication redirects, and protected routes without exposing or trusting user data.
3. Internal database values and domain identifiers such as `in_progress`, `review`, `ready`, priority values, and readiness verdict values remain unchanged.
4. Landing, login, dashboard, project list, project detail, and repository intelligence render without obvious truncation or overflow in both locales at representative desktop and mobile widths.
5. No credential, secret, data migration, business-logic change, or third-party runtime dependency is introduced.
6. Existing behavioral coverage remains meaningful in both locales, and lint, typecheck, the complete test suite, and production build pass.

### Constraints

- English is the default locale and Spanish remains fully supported.
- Keep localization small and first-party; do not add a third-party i18n dependency.
- Locale persistence must be server-readable so Server Components render the selected language on the first response.
- Preserve semantic HTML, accessibility names, focus behavior, pending states, and responsive design.
- Prefer standard US SaaS terminology and short action-oriented labels.
- Do not change logic merely to satisfy translated test assertions.
- Do not modify hosted data or production configuration during implementation.

## Develop handoff

Develop delivered the complete bilingual interface without adding a dependency or changing business, auth, database, or GitHub behavior.

- Added an allowlisted `en`/`es` locale model with English fallback and a server-readable, `HttpOnly`, `SameSite=Lax` preference cookie.
- Added a locale provider and native-button EN/ES control to the public header, authentication surface, and protected workspace shell.
- Localized metadata, landing content, navigation, auth, dashboard, projects, work items, repository intelligence, readiness evidence, form help, confirmations, validations, server-action feedback, dates, and loading/empty/error/not-found states.
- Preserved Spanish copy and internal enum/database values while making English the default for new visitors.
- Added focused locale, switcher, server-action, validation, readiness, and two-language UI coverage.
- Reported lint, typecheck, 133 tests, production build, and diff check passing after the correction round.

## Testing verdict

### Round 1 — REJECTED

Testing found one major behavioral regression: the language control submitted `usePathname()` without the current query string. Switching locale removed project `?status=review` filters and removed `?next=/projects` from the login route, changing the post-authentication destination.

All other criteria passed in round 1, including English server-rendered default, Spanish SSR, invalid-cookie fallback, cookie attributes, visible keyboard-accessible controls, complete localized states, no dependency/schema/secret changes, and real 390×844 layouts without horizontal overflow.

### Round 2 — APPROVED

Testing independently confirmed that query-bearing paths now survive locale changes, login returns to the retained destination, project filters remain active, and external/protocol-relative/encoded-path attacks still fall back internally. No blocker, major, or minor findings remained.

Round 2 checks passed: focused 29 tests, lint, typecheck, the full 133-test suite, production build, diff check, raw SSR locale responses, and real Chrome at 390×844 and 1280×900.

## Correction rounds

### Develop correction 1

- Combined the current pathname and `useSearchParams()` in the submitted return path.
- Kept redirect parsing against a fixed internal origin and applied encoded-separator rejection to the pathname, allowing safe encoded query values without allowing external navigation.
- Added component and server-action regressions for `/projects?status=review` and `/login?next=%2Fprojects`, plus unsafe destination coverage.
