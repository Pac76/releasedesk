# RD-003 — Authentication and protected app shell

## Task brief

Implement Supabase email/password registration and sign-in, confirmation-token handling, sign-out, Next.js 16 proxy cookie refresh, protected dashboard routing, and a defense-in-depth authenticated layout. The increment had to remain buildable without configuration, avoid privileged keys, sanitize redirects, and expose safe Spanish feedback without creating remote users during implementation.

## Develop handoff — initial implementation

Develop replaced the placeholder with accessible sign-in/register forms, added validated server actions, supported both immediate-session and confirmation-required signup, created the confirmation route, and protected the dashboard through a Next.js 16 proxy plus an independent server layout check. Initial checks passed with 26 tests and safe local HTTP redirects.

## Testing review round 1

**REJECTED.**

Testing found two MAJOR issues:

1. The server client discarded the response headers supplied by the current `@supabase/ssr` `setAll` contract. The email-confirmation route could therefore write session cookies without carrying the required private anti-cache headers.
2. Tests covered validation helpers and rendered forms but did not directly invoke the security boundaries: sign-in, signup, sign-out, confirmation handler, proxy decisions, or cookie/header propagation.

No commit or deployment occurred after this rejection. The findings were returned to Develop as a focused correction task.

## Develop correction

Develop added an explicit Supabase response context that captures both cookies and all library-supplied headers and finalizes route responses with strict private no-cache headers. The confirmation route now finalizes every success/error redirect through that context, and the proxy covers authentication cookie-writing paths while copying refreshed cookies and headers.

Direct mocked boundary tests were added for:

- sign-in validation, generic failures, normalization, and redirect sanitization;
- confirmation-required and immediate-session signup;
- sign-out and redirect behavior;
- confirmation success/failure plus cookie and anti-cache propagation;
- authenticated/unauthenticated proxy decisions, hostile redirects, refreshed cookies, and headers;
- the installed SSR `setAll(cookies, headers)` adapter contract.

The suite increased from 26 to 39 tests.

## Testing review round 2

**APPROVED.**

Testing independently re-inspected the installed `@supabase/ssr` behavior, header merge result, cookie propagation, proxy matchers, redirect boundaries, and the new direct tests. All RD-003 acceptance criteria passed with no BLOCKER, MAJOR, or MINOR findings.

Remote registration, confirmation email delivery, authenticated dashboard rendering, and hosted sign-out were deliberately not exercised because they would mutate external user state. Visual browser control was unavailable; accessibility and responsiveness were assessed from source, rendered markup, tests, build, and local HTTP behavior.

## Orchestrator verification

The Orchestrator inspected the actions, confirmation route, server client, response finalizer, proxy implementation, and React client boundaries. Server Components remain the default; client components are limited to interactive forms and error boundaries. No `getSession()` trust decision, privileged key, credential, or raw provider error was introduced.

## Result

RD-003 is approved after two review rounds. Hosted Auth settings, redirect allow-list/template configuration, and real evaluator-account verification remain external integration steps.
